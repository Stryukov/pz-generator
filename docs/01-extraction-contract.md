# Контракт на результат — извлечение данных (шаг 2)

Инструкция для **агента извлечения**.
Вход: контракт (этот файл) + **карта колонок под тип расчёта** + схема манифеста
(`docs/02-manifest-schema.md`) + расчёт (PDF или xlsx) + доп-контекст исполнителя
(тело письма/вложение).
Выход: манифест — JSON строго по схеме.

## Задача
Прочитать расчёт и доп-контекст и вернуть манифест: числа, флаги, реквизиты по делу.
Не пересчитывать, не форматировать, не додумывать — только точное извлечение.

## Контекст
- Данные пойдут в судебный документ — цена ошибки высокая.
- Расчёт — плотная таблица (много колонок по месяцам); часть полей может отсутствовать.
- Числа далее сверяются валидацией; при расхождении извлечение запускается повторно с
  обратной связью.

---

## 1. Формат
- Строго JSON по схеме `02-manifest-schema.md`. Без текста, пояснений и Markdown вокруг.
- Числа — сырые, разделитель дробной части — точка (`11273.59`). Никаких пробелов, запятых,
  «руб.», «м³».
- Даты — `YYYY-MM-DD`; месяцы — `YYYY-MM`.

## 2. Обязательное
- Флаги выводятся **из расчёта**:
  - `has_nvcs`, `has_p203`, `has_gvs` = true, если в расчёте есть соответствующая сумма/колонка.
  - `k_coefficient = sum_nvcs / sum_stoki` (округлить до 0,5 или 2,5, если попадает в допуск).
  - `has_seasonality` = true, если объём стоков ГВС меняется по месяцам (есть/ноль).
  - `is_recalc` = true при признаке повторного расчёта в связи с поверкой.
- `nvcs_mode` = `p123_4` по умолчанию; `razdel_13` — только если задано в доп-контексте.
- Извлечь **все** месяцы периода в `months[]`.
- **Суммы — итоговые с НДС**: у начисления в расчёте три колонки (без НДС / НДС / с НДС) —
  в манифест идёт колонка **с НДС** (`sum_hvs`, `sum_stoki`, `sum_nvcs`, `sum_p203`, `month_total`).
- Извлечь **все тарифные интервалы** в `tariffs[]` — тариф может меняться внутри периода
  (напр. до 30.06 и с 01.07).
- Выбрать `example_month`: первый месяц; если он нулевой/частичный/нетипичный — ближайший
  типичный (и это должно быть видно валидации/исполнителю).
- Ненайденное поле → `null` + путь поля в `issues.missing`.
  ⚠️ В `issues.missing` попадает **только то, чего нет ни в расчёте, ни в доп-контексте**.
  Если значение восполнено доп-контекстом — это **не пропуск**, в `missing` его не писать
  (иначе манифест противоречит сам себе: поле заполнено и одновременно помечено пропущенным).
  Пример: даты договора нет в расчёте, но исполнитель прислал её → `missing` пуст по этому полю.
- **Приоритет источников: доп-контекст → расчёт → `null` + `issues.missing`.** Если поле есть в
  обоих — доп-контекст **переопределяет** расчёт (исполнитель знает контекст дела). Конкретно:
  - `ispolnitel`, `objects` (адрес+назначение) — есть в доп-контексте → оттуда; нет → **фоллбэк
    на расчёт** (правила в §4); нет нигде → `null` + `missing`;
  - `normativ_npa`, `nvcs_mode_override` — **только** доп-контекст (в расчёте источника нет):
    не заполнено → `null` + `missing`, фоллбэка нет.
- В таблицах доп-контекста источник данных — **только столбец «Ваше значение»**. Столбец
  «Пример заполнения» (и любые примеры в шаблоне) **игнорировать полностью**: пример — не данные.
  Пустое «Ваше значение» → поле отсутствует (`null` + `issues.missing`).

## 3. Запреты
- Не выдумывать и не «додумывать» числа, даты, реквизиты, НПА. Нет данных → `null`.
- Не пересчитывать и не «исправлять» суммы — извлекать как в расчёте (пересчёт делает валидация).
- Не форматировать числа (никаких `11 273,59`, только `11273.59`).
- Не интерпретировать юридический режим за пределами правила `nvcs_mode`.
- Не заполнять `issues.assumption` — это делает валидация.

## Карта колонок
Карта колонок под конкретный тип расчёта приходит **отдельным документом** (в том же system-
промпте, раздел «Карта колонок — …»). Работай только по ней. Общее правило для всех карт:
колонки определять **по заголовкам, НЕ по позициям** — состав, порядок и количество колонок
меняются от абонента к абоненту и от файла к файлу (расчёты дорабатываются вручную).

Продублируй в манифест поле `doc_type` из заголовка полученной карты — это страховка от того,
что типом ошиблись до тебя.

## НДС: определять из расчёта, не по умолчанию
Конвенция НДС различается: для **ФЛ** (население) НДС уже включён в тариф, для **ЮЛ** —
начисляется сверху. Поэтому жёсткого правила «тариф без НДС» нет.

**Главный признак — строка нумерации колонок** (`1`, `2`, `3`, … под заголовками). В части
расчётов там прописаны формулы:
- формула суммы содержит множитель `1,2` (напр. `12=6*4*1,2`) → **тариф без НДС**,
  самопроверка `сумма ≈ V × тариф × 1,2` действует;
- формула без множителя (напр. `18=13*7`) → **тариф уже с НДС**, сумма = `V × тариф`.

Формул нет → определить арифметически на первом непустом месяце: если `V × тариф` совпадает с
суммой — тариф с НДС; если совпадает `V × тариф × 1,2` — тариф без НДС.
Записать вывод в `tariffs[].nds` (`"with"` / `"without"`) — валидация опирается на него.

⚠️ Заголовок суммы «руб. с НДС» относится к **сумме**, а не к тарифу, и стоит в обоих случаях —
по нему конвенцию НДС определять нельзя.

## Самопроверка перед возвратом (обязательный шаг, не пожелание)

Заголовки неоднозначны, а колонки идут группами «слагаемое, слагаемое, итог» — легко взять
слагаемое вместо итога. Поэтому **до того, как вернуть манифест**, выполни проверки ниже.
Не сошлось — **манифест не возвращать**: вернуться к карте колонок, найти итоговые колонки
групп (со словом «Итого»/«Всего») и пересобрать месяц.

1. **Сходимость месяца.** Для каждого месяца:
   `sum_hvs + sum_stoki (+ sum_nvcs, если has_nvcs) (+ sum_p203, если has_p203)` = `month_total`
   (допуск ±0,05).
   Не сходится — почти всегда взято слагаемое вместо итога группы. Типовой промах: вместо
   «Всего к оплате стоки ХВС и ГВС» взята «Сумма к оплате стоки ГВС».
2. **Согласие с тарифом.** `sum_hvs ≈ V_hvs × тариф_ХВС × k` и
   `sum_stoki ≈ V_stoki × тариф_стоки × k`, где `k` = 1,2 при тарифе без НДС и 1,0 при тарифе
   с НДС (см. §НДС). Не сходится ни при `k=1,2`, ни при `k=1,0` — взята не та колонка объёма
   или суммы.
3. **Сходимость итогов.** `totals.charged` = сумма `month_total` всех месяцев;
   `totals.balance` = `charged − paid`.

Проверки 1 и 2 выполняются на **каждом** месяце, а не только на `example_month`: именно они
ловят перепутанные колонки. Валидация на следующем шаге делает ровно эти же проверки — если
ты выполнил их сам, повторное извлечение не понадобится.

## 4. Детализация
- **Суммы — с НДС** (см. §2): `sum_hvs`, `sum_stoki`, `sum_nvcs`, `sum_p203`, `month_total` —
  из **итоговой колонки с НДС**, не «без НДС».
- `month_total` — **итоговая сумма за месяц с НДС** (последняя итоговая колонка строки),
  НЕ колонка п.203 и не промежуточный итог.
- `sum_p203` — из **колонки п.203** (с НДС); `has_p203=true` только если такая колонка есть.
- `V_stoki` — из колонки **водоотведения** расчёта; **может отличаться** от `V_hvs`
  (объём стоков задаётся отдельно). `V_gvs` — только при `has_gvs`.
- `tariffs`: по каждому интервалу — `date_from`/`date_to`, `tariff_hvs`, `tariff_vo`, `nds`
  (`with` / `without` — ровно как в расчёте). Интервалов может быть несколько.
- `pu_list`: по одной записи на прибор (объект, номер, дата поверки; нет даты → `null`).
  **Фоллбэк на адреса:** нет данных ПУ, но в расчёте есть колонка с адресами объектов
  («Объект водопотребления и водоотведения, адрес») → заполнить по одной записи на
  **уникальный** адрес: `{ "object": "<адрес>", "meter_no": null, "poverka_date": null }`.
  Порядок — как в расчёте; адреса дедуплицировать (в xlsx-выгрузках адрес повторяется в
  каждом месяце). `[]` — только если в расчёте нет ни ПУ, ни адресов.
- `executor_context.objects`: список `{address, purpose}` из доп-контекста (таблица объектов).
  `purpose = null`, если назначение не указано. Пустой список или `"DELETE"` в `purpose` — если
  исполнитель просил удалить блок назначения.
  **Фоллбэк:** нет таблицы объектов в доп-контексте → взять те же уникальные адреса из расчёта,
  `purpose = null` (назначения в расчёте нет — оно станет плейсхолдером).
- `executor_context.ispolnitel`: строка `"ФИО, должность"`. Нет в доп-контексте → **фоллбэк на
  расчёт**: под таблицей бывает блок подписи — строка «Исполнитель:», далее **должность** и
  **ФИО** отдельными строками. Собрать как `"ФИО, должность"`
  (напр. `"Докучаева Е.А., Ст. специалист по работе с ЮЛ ЕРЦ"`). **Отбросить** телефон
  (`тел. …`) и строку с датой/подчёркиванием подписи. Блока нет → `null` + `missing`.
- `totals`: `charged`, `paid`, `balance` — из строк «Итого / Оплачено / Остаток» расчёта.
- `months[].sewage_percent` и `flags.sewage_percent`: процент канализирования =
  **объём стоков ХВС ÷ объём ХВС** (в процентах, округлить до 0,1). ⚠️ Именно стоки **ХВС**,
  а не итог стоков: стоки ГВС — отдельный поток и в базу не входят. Считать по каждому месяцу;
  в `flags` — **преобладающее** значение. Если у части месяцев процент иной — перечислить эти
  месяцы в `issues.assumption` («в [месяц] процент канализирования иной ([X] %) — проверьте»).
  Стоки равны потреблению (100 %) → `sewage_percent = 100`, пояснение в записке не понадобится.
  `V_hvs = 0` → `sewage_percent = null` (делить не на что).
- `executor_context.sewage_reason`: причина, по которой стоки не равны потреблению — **только**
  из доп-контекста. Из расчёта её взять нельзя; нет — `null` + `issues.missing`.
- `months[].calc_basis`: `"pu"` — есть объём «по прибору учёта»; `"norm"` — только «по нормативу»;
  **`"average"` — ТОЛЬКО если исполнитель указал этот месяц в доп-контексте** как посчитанный по
  среднему. Из расчёта расчёт по среднему **не виден** — самостоятельно его не выводить.
- `months[].has_adjustment`: `true`, если в колонке оплаты (или «Дата, № п/п») вместо суммы стоит
  пометка о корректировке (напр. `корректировка долга`). Саму пометку в суммы не переносить.
- `example_months`: по одному месяцу на каждый **различающийся вариант расчёта** — группировать
  месяцы по паре (`calc_basis`, `sewage_percent`) и брать из каждой группы репрезентативный
  (не нулевой, не сторно). ⚠️ Месяцы с `sewage_percent = null` (нулевой ХВС) **своей группы не
  образуют** — они относятся к преобладающему варианту и покрываются фразой «аналогичным
  способом». Обычно вариант один; несколько — только когда месяцы реально считались по-разному. `example_month` = первый элемент списка. Если исполнитель просил
  расписать все месяцы (`executor_context.expand_all_months`), список всё равно заполняется
  обычным образом — раскрытием займётся генерация.

## 5. Готово когда
- Манифест валиден по схеме, все обязательные секции присутствуют.
- Все ненайденные поля перечислены в `issues.missing`; выдуманных значений нет.
- Флаги согласованы с числами: если `has_p203=true` → у месяцев есть `sum_p203`; если
  `has_gvs=false` → `V_gvs=0` во всех месяцах.
- Числа — сырые, без форматирования; даты в ISO.
