## [Unreleased]
### Fixed
- **Записка приходила с текстом «Ошибка разбора ответа генератора» и сырым JSON вместо
  документа.** Модель обрамила ответ рассуждением («Разберём манифест: has_gvs=true, но…»), а
  `Parse Output` делал `JSON.parse` всего текста — преамбула ломала разбор, и фоллбэк вываливал
  сырой ответ в `html`. Оба узла разбора (`Parse Output` и `Parse Manifest` — код был одинаковый
  и уязвимость тоже) получили **толерантный разборщик**: снять ```-обрамление → `JSON.parse` →
  не вышло, взять подстроку от первой `{` до последней `}`. Проверено оффлайн на пяти входах:
  чистый JSON, с преамбулой (реальный случай), в ```-обрамлении, с хвостом после JSON, мусор
  без JSON (корректно даёт фоллбэк). Промпты трёх агентов дополнены требованием «ответ
  начинается с `{` и заканчивается `}`, рассуждай про себя» — защита в два слоя.
- **`issues.missing` противоречил сам себе**: поле, восполненное доп-контекстом, всё равно
  помечалось пропуском. Именно на этом противоречии модель и начала рассуждать вслух. Теперь в
  `missing` попадает только то, чего нет **ни в расчёте, ни в доп-контексте**.
- **Адрес переписывался** вопреки правилу «как в расчёте»: `г.Елизово, Ленина ул., 49б кв.пом 1`
  превращался в `г. Елизово, ул. Ленина, 49б, кв. пом. 1`. Правило ужесточено до
  **посимвольного** совпадения, с примерами верного и неверного вывода. Заодно описан разбор
  ячейки вида «адрес**:** описание объекта»: адрес — до двоеточия, а хвост идёт в «Назначение»,
  если исполнитель не дал своего.
- **Подпись собиралась как «ФИО, Должность»** вместо «Должность ФИО» — порядок закреплён явно.
- **Шум в комментариях исполнителю** («проверьте актуальность», «проверьте корректность
  источника»): `docs/05` получил закрытый список того, что вообще может попасть в
  `executor_notes` — комментарий нужен, только если исполнителю есть что доделать.
- **В записку попадала причина, которой не было ни в расчёте, ни в доп-контексте** («в связи с
  тем, что часть сточных вод сливается в септик»). Модель не выдумывала — формулировка была
  **зашита в болванку** `sewage_percent` при переносе из образца 1144 вместе с обоснованием.
  Теперь причина подставляется дословно из `executor_context.sewage_reason`, нет — плейсхолдер
  + напоминание исполнителю. Дословный пример убран из всех файлов, уходящих в промпт, чтобы
  модель не подхватила его как типовой.
- **Неверная база процента канализирования** разносила месяцы по ложным «вариантам расчёта»:
  процент считался как `итого стоки / ХВС`, а итог включает стоки ГВС. В 1139 стоки ГВС
  постоянны (11,638), ХВС меняется → отношение прыгало (266 / 411 / 213 / 333 %), давая пять
  групп и **пять месяцев-примеров вместо одного**. Верная база — **стоки ХВС ÷ ХВС** (ГВС это
  отдельный поток и в базу не входит): 1139 → 100 % во всех месяцах → один пример; 1144 →
  20,4 % (авг/сен) и 100 % (окт) → два примера. Месяцы с нулевым ХВС дают `sewage_percent = null`
  и своей группы не образуют.
- **Извлечение брало слагаемое вместо итога группы** — на реальном прогоне (1139 с лишней
  колонкой) модель взяла «Сумма к оплате стоки **ГВС**» (1 075,78) вместо «**Всего** к оплате
  стоки ХВС и ГВС» (1 722,83); валидация ловила ошибку и запускала повторное извлечение, то есть
  лишний платный вызов на каждом таком письме. Причина не в невнимательности модели: шапка
  размазана по 2–3 строкам с объединёнными ячейками, после `xlsx2csv` заголовок сопоставляется
  с колонкой только позиционно, а лишняя колонка сдвигает позиции. Исправлено в `docs/01`:
  (1) явно описана **групповая структура колонок** («слагаемое, слагаемое, итог») с правилом
  «в манифест идёт только итог группы»; (2) добавлен **разобранный пример** реальной строки —
  какое число из какой колонки в какое поле; (3) §«Самопроверка» переписана из перечня пожеланий
  в **обязательный алгоритм перед возвратом** (сходимость месяца, согласие с тарифом, сходимость
  итогов) — это те же проверки, что делает валидатор, так что модель чинит себя сама.

### Added
- **Свой вид записки для Прочих ОН** (`docs/04-spec-prochie-on.md` +
  `templates/document-template-prochie-on.json`, эталон — `examples/1144 Пояснительная.docx`):
  договорный абзац, формулы через `+ 20% (НДС)`, помесячная расшифровка, блок корректировки,
  подпись «Должность ФИО ____». Блоки НВЦС и п. 203 заложены заранее и включаются флагами —
  когда придёт пример «Прочие ОН с НВЦС», правок шаблона не потребуется. Тип `prochie-on` в
  `types.json` переключён на них; **флоу не менялся** — маршрутизация подхватывает новые файлы.
- **Месяцы-примеры по вариантам расчёта**: `manifest.example_months` — по одному примеру на
  каждую комбинацию (основание расчёта + процент канализирования), а не один на всю записку.
  Иначе месяц, посчитанный иначе (напр. по среднему), просто не попадал бы в документ.
  `executor_context.expand_all_months` — расписать все месяцы по явной просьбе исполнителя.
- **Процент канализирования**: `flags.sewage_percent` / `months[].sewage_percent` — стоки могут
  быть не равны потреблению (часть уходит в септик; в 1144 — 20,4 %). При проценте < 100 в
  записку добавляется пояснение. Месяцы с иным процентом в текст не выносятся — уходят
  комментарием исполнителю.
- **Расчёт по среднему** (`months[].calc_basis = "average"`): из расчёта не виден, поэтому
  пометка «по среднему в связи с отсутствием показаний» ставится **только** если исполнитель
  указал месяц в доп-контексте.
- **Корректировка долга** (`months[].has_adjustment`): в расчёте вместо суммы оплаты бывает
  пометка, суть которой не видна. Текст собирается **болванкой с подстановкой** того, что дал
  исполнитель; чего нет — плейсхолдер, факты не домысливаются. Пояснения нет вовсе → болванка
  с плейсхолдерами + напоминание исполнителю в ответном письме.
- **Маршрутизация типов расчёта** (`templates/types.json` + узлы `Fetch Types` / `Detect Type` /
  `Fetch Columns`). Тип определяется **до извлечения** по маркерам (имя файла, `calc_type`,
  подстроки текста), после чего карта колонок, спека и шаблон качаются по **динамическим URL**.
  Таблица типов лежит в репозитории → **добавление нового типа = запись в JSON + файлы, без
  правок флоу** (конвенция «флоу статичен»). Предикаты: `calc_type`, `filename_contains`,
  `text_all`, `text_any`, `text_none`; первое совпадение выигрывает, иначе `default`.
- `docs/01` разделён: общая часть контракта + карты колонок по типам
  (`01-columns-format-A.md`, `01-columns-prochie-on.md`). Агент извлечения получает **одну**
  карту вместо всех — меньше шансов перепутать формат, и `docs/01` перестаёт расти с каждым
  новым типом.
- **Подтверждение типа**: манифест получил поле `doc_type` (агент проставляет его по заголовку
  полученной карты), оба `Validate` сверяют его с типом от детекции и отдельно ловят
  `doc_type_matched=false` (ни одно правило не сработало → применён `default`). Ошибка
  маршрутизации всплывает **до генерации**, а не в готовой записке.

### Changed
- **Единая таблица объектов во всех записках**: `№ | Объект | Назначение | Прибор учёта |
  Дата поверки` заменила прежнюю ПУ-таблицу **и** отдельный абзац «На объекте по адресу …
  располагается …». Блок 2 Типа А удалён (нумерация остальных блоков сохранена, чтобы не ломать
  ссылки); назначение выводится колонкой. В `templates/executor-context.md` Таблицы 2 и 3 слиты
  в одну, добавлена Таблица 3 «особые обстоятельства» (по среднему, корректировка, расписать все
  месяцы) с пояснением, почему эти данные нельзя взять из расчёта.
- Порядок узлов: конверсия расчёта (`Calc Type? → … → Calc Text`) поднята **выше** Fetch-узлов —
  без текста расчёта тип определить нельзя. `Load Contracts` теперь склеивает
  `extraction_system` = общая часть + карта колонок + схема.
- **Правило НДС переписано** (`docs/01` §«НДС»): жёсткое «тариф без НДС» заменено на определение
  **из расчёта**. Для ФЛ (население) НДС уже в тарифе, для ЮЛ — сверху. Главный признак —
  строка нумерации колонок: формула с `×1,2` (`12=6*4*1,2`) → тариф без НДС; без множителя
  (`18=13*7`) → тариф уже с НДС. Заголовок «руб. с НДС» относится к сумме, не к тарифу, и для
  определения конвенции непригоден. Проверено численно на Прочих ОН и на УК.
- Карта «формата B» переименована в **Прочие ОН** и обновлена под стандартизованный образец
  (`1139 ОБРАЗЕЦ`): колонка «Дата, № счет-фактуры»; правило игнорировать подколонку
  «по прибору учета» у стоков ГВС (её скрывают — стоки по прибору практически не считают);
  явное указание, что нулевой ХВС при ненулевых стоках — **не** сторно; «Корректировка долга»
  в записку не выводится.

### Fixed
- xlsx-ветка: биллинговые выгрузки имеют **сломанный `<dimension>`** (заявляет меньше строк, чем
  есть) → n8n `Extract from File`/SheetJS читал только 2 месяца из 13. Заменено на конвертацию
  **xlsx2csv** через Execute Command (`Write Calc XLSX → XLSX to CSV → Cleanup XLSX`), которая
  читает реальные строки. Требует `python3` + `pip install xlsx2csv` в контейнере.
- Валидатор (`Validate`/`Validate 2` + `docs/03`): null-guard тарифного интервала —
  не падать `schema:…null…slice` при `date_to: null` (открытый интервал трактуется как «до конца»).
- Верификация сборки: все Code-узлы прогоняются через `node --check` (ловит реальный LF внутри
  JS-литералов — прежний класс ошибок).

### Added
- Спецификация записки (структура, вариации, источники) — Тип А.
- JSON-шаблон сборки (флаги, дословные болванки) — Тип А.
- Мини-шаблон доп-контекста для исполнителя.
- Каркас репозитория, README, заглушки контракта и флоу.

- Документ извлечения и валидации: схема манифеста, контракт агента извлечения, правила валидации (пример-месяц + итоги).

- n8n workflow (импортируемый JSON) + инструкция; контракты подгружаются из репозитория, флоу статичен.

### Changed

  в шрифтах Type0/CID) на **poppler `pdftotext -layout`** (узлы `Write Calc PDF` + `PDF to Text`
  через Execute Command; `Cleanup PDF` удаляет temp-файл). Заголовки колонок теперь читаемы.
- docs/01: добавлена **карта колонок по заголовкам** (устойчива к отсутствию групп НВЦС/п.203
  и к разному числу тарифных интервалов).
- Бета: в генерацию подгружается `templates/document-template-type-A.json` (узел
  `Fetch Template`) — модель получает дословные болванки и шаблоны блоков, а не пересказ.
- Бета: контракт извлечения (`docs/01`) + схема (`docs/02`) — помесячные суммы берутся
